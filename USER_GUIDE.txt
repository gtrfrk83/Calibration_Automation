CALIBRATION SUITE - QUICK START (v70 Beta)
===========================================

Starting
  Double-click Start_Calibration_Suite.bat (or run:  py -3 Calibration_Procedure_Manager.py).
  If add-on packages are missing, a message tells you exactly what to type to install them.

Your data
  Your databases and saved progress are in your own data folder (Help > Open my data folder), normally
  C:\Users\<you>\AppData\Local\CalibrationSuite-Beta\
  The beta never touches the released copy. To try the beta with the released copy's data:
  Help > Import data from another copy...  and choose the released copy's folder. Files are COPIED; the original is not changed.

Running a verification
  1. Pick the procedure in the Manager (or double-click the instrument in Instruments) and press Run procedure.
     "Try in demo mode" needs no instruments. It connects VIRTUAL instruments: you see the same windows as a real run (connection, reset
     notice, hook-up and function prompts, the reading window, per-point windows, Edit point) and every command goes through the real driver to a
     simulated instrument. Where you type the reading (handhelds), a "Fill with a simulated reading (DEMO)" button offers an in-tolerance value;
     you may type anything instead, and "Include some failures" makes some filled points fail. Waits are shortened. Everything is marked DEMO:
     window titles, the banner, every report page; nothing goes into Asset History or the lab registry. "Fast demo (no windows)" keeps the old
     quick demo. The WaveSurfer and the 8846A adjustment procedure still use their older demo (canned data / no instrument commands).
  2. Enter the Instrument ID and serial number, check the connections, press Test connections.
  3. Run All Pending. The program stops and asks you to confirm wiring before each new set-up. Outputs go to standby after every point.
  4. Save progress (Ctrl+S) any time; Load progress (Ctrl+O) to carry on later.
  5. Export Report (PDF) (Ctrl+P): the "Calibration Data" report, named <asset>-<date>.

Run queue: several handheld meters in one session (Fluke 110 series, 77 IV, 87V, 170 series, 287 / 289, Klein MM325)
  Use it when you have several meters of the SAME model to verify. With one meter nothing changes: the procedure runs exactly as before.
  1. Press "Connections", then "Run queue..." (under "Several meters"). The window lists the meters: asset number (typed, or chosen from Asset History,
     which also fills the serial), serial, technician. Add meter / Edit / Remove / Move up / Move down. An asset can be listed once.
  2. Choose how to run them.
     Point by point (recommended): all meters are wired to the calibrator together. Each point is set ONCE (calibrator output, settle, OPERATE as usual);
       then ONE window asks for the reading of meter 1, 2, 3, each box labelled with the asset number. Every box is judged at once against the point's limits
       (PASS / FAIL, padding to the resolution as usual). Enter moves to the next box; Enter in the last box, or "Record all (Enter)", stores the point for every
       meter. "No reading" on a row leaves that meter without a result for that point. "Skip point" and "Stop run" apply to the whole queue.
       Hook-up, function and meter-setup prompts appear once per group and name every meter. The high-voltage question is asked once for each high-voltage point
       (as before) and names every meter on the leads.
       Points that cannot be shared are done one meter at a time, with a prompt that tells you why and which meter to connect: current points (the meters would
       have to be in series), 4-wire resistance, VoltAlert, the 87V duty-cycle / square-wave points, and points set by hand. Voltage, resistance, frequency,
       capacitance and temperature points are shared.
     One meter at a time: the normal procedure runs for meter 1 to the end, then you are asked to swap in meter 2, and so on. Over the IR cable (287 / 289) this
       is the only choice (one cable, one meter).
     The window says what the choice saves, e.g. "40 points x 3 meters = 120 settings one at a time; point by point needs 50".
  3. "Start queue" runs the pending points of every meter. "Save (do not start)" keeps the list; then Run All Pending, Run Shown Section and Rerun Selected use it
     (a chip at the top says "Run queue: 3 meters"). Remove meters until one is left to go back to the single-meter run.
  4. A small "Queue progress" window shows, per meter, how many points are recorded and how many failed. A failure on one meter never stops the others.
  Each meter keeps its own results, As Found / As Left, saved progress, report and Asset History record. Nothing is merged between assets.
  Reports: "Export Report (PDF)" offers one "Calibration Data" report for every meter (asset#-date, the technician from the queue); a file that already exists is
  never overwritten. The progress window has the same "Export all reports (PDF)..." button when the run ends, and "Show" to look at one meter's results.
  Resume: saved progress (checkpoint) is kept per meter. Run the queue again with the same assets and you are asked once whether to continue from it; points
  already recorded are not measured again. Demo progress is never resumed by a real run.
  Not supported: meters whose procedure modifications (Edit point, saved for an asset) differ from each other (the queue shares one set of points and limits; run them
  separately), and user-built datasheets (Datasheet Builder).
  Demo mode: the queue runs on the virtual bench; "Fill with a simulated reading (DEMO)" fills every box; reports are marked DEMO and nothing reaches Asset History.

As Found and As Left
  "Collecting data" = As Found: the first measurements, before any adjustment.
  If the instrument was adjusted, switch to As Left and run the points again. The As Found readings are kept.
  If nothing was adjusted, stay on As Found: the report prints "Same" under As Left.
  Run Shown Section: choose a section in the Show box, then press it to measure just that section.

If something goes wrong
  A plain message appears and a diagnostic log is saved (Help > Save diagnostic log for support). Send that file to your lab support contact.
  Saved results are not affected. Passwords are never written to logs.

Keys:  Ctrl+S save progress   Ctrl+O load progress   Ctrl+P export PDF   F1 About

The test window (beta layout)
  Left: the sections of the procedure with a coloured dot (blue = in progress, green = all pass, red = something failed) and how many are done.
  Top: Instrument ID and serial, the As Found | As Left switch, and the progress ring.
  Connections: press "Connections" (top right) to set the instrument addresses and ports; Test connections is at the bottom of that panel. Esc closes it.
  Bottom: Run All Pending, Run Shown Section, Rerun Selected, Stop, then Save / Load / Export.
  Small screens: below about 1100 pixels wide the section list becomes a drop-down and Low / High limits share one column.
  Look: Help > Appearance chooses Dark or Light for the next window you open.

Verified on hardware (Procedures list)
  The "Verified on hardware" column says which procedures have been run correctly on the real instruments, and when.
  After a procedure has run correctly on the actual hardware, select it and press "Mark verified on hardware..." (who verified it, the date, and optionally the
  instrument and calibrator used). It is then LOCKED: the procedure changes window, the "Edit point" control in the running window, developer-mode edits and
  the Datasheet Builder (new version, delete) all refuse, with a message saying it is verified and locked. Running it is not affected, and changes that were
  saved before it was locked stay as they are.
  To change a locked procedure: select it, press "Unlock for editing..." and type the reason (your name, the date and the reason are recorded). Afterwards press
  "Lock again" if nothing changed, or verify it on the hardware again. Anyone can unlock; nothing is hidden.
  If a program file or test-point file of a verified procedure is replaced by an update, it is no longer verified: it is unlocked automatically (recorded as
  "system", with the changed files) and the column shows "Changed since verification - needs hardware re-verification" until someone runs it on the hardware and
  presses "Mark verified on hardware..." again. Updates are never blocked. "Unlock for editing" (with a reason) is for when nothing has changed.

Importing a procedure package (Procedures list)
  A package is a zip file that carries one procedure (its launcher, test points and limits, driver, hook-up diagrams, tests) from another copy of the suite
  or from a colleague. It holds PYTHON PROGRAM CODE that will run on this computer, so only import packages from the lab's own library folder.
  Library folder: on the Procedure Development tab, under "Procedure packages", press "Choose folder..." and pick the shared folder where the lab keeps its
  packages (a network drive, for example). It is empty until you set it. The file picker of the import then opens there.
  To import: press "Import procedure package..." (top right of the Procedures list) and pick the zip. A window shows what it is BEFORE anything is written:
  the name and version, who it says made it, where the file is (and whether that is inside the library folder), every file in it and whether the file is new,
  replaces an installed file or is identical, whether the procedure is verified on hardware and locked right now, and what the package would do about that.
  Tick "I know where this package came from and I want to install it", then press "Install package". Cancel installs nothing.
  A package is refused (with the reasons listed, and no Install button) if a file's checksum does not match, a file is missing or not listed, a path tries to
  leave the suite folders, a file is outside Procedures / specs / drivers / diagrams / tests, a program or database file type is not allowed, a Python file is
  not valid Python, it needs a newer suite, or it needs files this copy does not have.
  Every installed file that replaces one is first copied to Backups\packages\<folder>\<name>_backup_v01 (v02, v03 ... next time). If anything fails part way,
  the files already written are put back. The import (which package, when, by whom, the files) is recorded in the lab registry (Asset History database).
  A new procedure appears in the Procedures list straight away. Nothing is hidden or hosted: the package is just a file in a folder.
  Verified on hardware: if the package REPLACES files of a procedure that is verified and locked, the window warns you and, once installed, the procedure is
  unlocked (recorded as "package import") and needs hardware re-verification. The only exception is a package that carries a verified mark (date and name of
  the person who verified it, plus a fingerprint of the files) whose fingerprint matches the files now installed and where this copy has no saved procedure
  changes for that model: then the procedure is marked verified and locked again with that date and name. The mark shows that the files are the ones that were
  verified; nobody here has re-checked an instrument. Other locked procedures that use a replaced shared file (a driver, an engine) show "Changed since
  verification" as usual, and the window names them.
  Making a package (on the computer that has the procedure): python tools\make_package.py <procedure id> --out <library folder>
  (python tools\make_package.py --list shows the ids). Add --verified-mark to attach the verified mark, --include <file> to ship an extra file.

  Files that decide "Changed since verification": each procedure lists, in Procedures\<id>.procedure.json, exactly the files it depends on. Editing the
  test points of one Fluke 110-series model, or the hook-up text of another meter, no longer unlocks the others. A shared engine or driver (for example
  handheld_dmm.py, drivers\fluke_5560a.py) still unlocks every procedure that runs on it.

Editing one test point (right-click > Edit)
  In a running procedure, right-click a test point and choose Edit (or select a point and press "Edit point"). A small window opens for that point only.
  It is disabled, with the reason, on a procedure that is verified on hardware and locked, and while that point is being measured.
  Commands: the list shows the instrument commands the procedure will send for this point, in order, with this point's real values. Each line shows the
  read-back query, its risk, and whether it is verified or UNVERIFIED. Select a line to change it; "Restore default" puts it back. Output and
  locked commands cannot be changed (the reason is shown). You can also add lines to send before or after the point. A line that sets something needs the
  query that reads it back and the reply to expect. It is sent once, read back and compared; if it does not match, the point stops and nothing is retried.
  Anything you type is recorded as UNVERIFIED. Outputs go to standby after the point as always. "Not tested" means the program has no safe way to try a command.
  No passphrase is needed to type or change a command (or add a before/after line) for THIS RUN ONLY: nothing is saved, it is gone when the instrument ID
  changes or the window is closed, and it is still recorded in this run's audit trail (who, when, old, new, reason), UNVERIFIED, and marked DEMO in demo mode.
  Saving a command change for this instrument or for all of this model (or taking a saved one away again) does need developer mode.
  Developer mode: press "Turn on developer mode..." and enter the developer passphrase (the same one as everywhere in the suite; it locks itself again after 15
  minutes without use). Only then can you change the tolerance (low/high or plus-minus), the unit, the nominal and the description of the point, or choose
  "This asset" / "This model". Without it those fields are read-only and the saved choices are greyed out. Changing a tolerance changes pass/fail, so you must type a reason and tick the acknowledgement. If the point already has a reading
  it is measured again against the new limit.
  Choose "This run only", "This asset" or "This model". Changes start at the next point, never in the middle of one. Every change is recorded (who, when, old,
  new, reason, point). PDF reports are unchanged. Demo mode is marked DEMO and always run-only. The WaveSurfer procedure shows no commands (tolerance only).
